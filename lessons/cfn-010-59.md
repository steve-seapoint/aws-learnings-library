# A Completed Wait Condition Never Waits Again

**Problem:** The first deploy waits for the instance's boot signal as intended. Later deploys change the user data or AMI, CloudFormation replaces the instance, and the stack goes to `UPDATE_COMPLETE` within seconds, before the new instance has finished booting. A broken boot on the replacement goes unnoticed. The same happens when the AMI comes from an SSM parameter lookup and AWS publishes a new image: the instance is replaced on an unrelated deploy with no wait at all.

**Root Cause:** A `WaitCondition` is satisfied once. Updating the instance does not reset it, and signals sent to its handle after completion are ignored. Only a *new* wait condition resource, with a new logical ID, waits again.

**Solution:** Give the handle and the wait condition logical IDs that change whenever the instance would be replaced. Hash the boot script (minus the handle URL, which can't contain its own hash) together with the AMI, instance type and subnet, and append it to both IDs. In CDK:

```python
fingerprint = f"{boot_script_without_handle}\n# {image_id} {instance_type} {subnet_id}"
suffix = hashlib.md5(fingerprint.encode()).hexdigest()[:8]
handle.override_logical_id(f"BootHandle{suffix}")
condition.override_logical_id(f"Boot{suffix}")
```

When the values are tokens resolved at synth time (the AMI map, subnet refs), compute the hash in a lazy producer so it sees the resolved template values rather than token placeholders. Pin the AMI ID instead of looking it up at deploy time: a deploy-time lookup can replace the instance without changing anything your hash can see.

Add a unit test that changes the AMI and asserts both logical IDs change. It is the only cheap way to catch a fingerprint that missed an input.

**Key Insight:** A wait condition checks one instance, once. Tie its identity to the instance's identity, or every replacement after the first goes unchecked.
