# A Silently-Succeeding Lambda Can Also Bypass the SQS DLQ

**Problem:** Three SQS messages cycled through the retry budget and landed in the DLQ, but not because the Lambda crashed or raised an exception — it returned `{"ok": True}` every time. The underlying work (an LLM-powered page rebase) was silently skipped on each attempt. No error appeared in CloudWatch. The DLQ trip happened only because a *secondary* failure (recursion-depth ceiling) eventually caused a real exception — by which point the retry budget was exhausted and the root cause had never been surfaced.

**Root Cause:** The LLM client raised an internal error (`stop_reason == "max_tokens"`) indicating its response was truncated, converted it into a structured `LlmError`, and the merge engine caught it and logged `merge.edit_skipped` — then continued and returned success. From SQS's perspective: message delivered, function returned, message deleted. `ApproximateReceiveCount` incremented normally each time, so `maxReceiveCount=3` was reached and the messages moved to the DLQ — but only after three expensive, token-burning, work-skipping invocations.

This is the **silent-success variant** of the DLQ-bypass problem documented in `sqs-002-29`. Where sqs-002-29 covers functions that *die* (crash/OOM) and never increment the receive count, this variant covers functions that *live* but produce a hollow result — the receive count increments correctly, the DLQ is eventually reached, but only after the full retry budget is burned on attempts that were doomed from the start.

**Solution:**

- **Treat non-error failure conditions as exceptions at the handler boundary.** If a core operation (LLM call, DB write, external API) produces a result that means "this invocation accomplished nothing useful," raise an exception rather than returning success. Let SQS count it as a failed delivery.
- **Distinguish retriable from non-retriable failures before burning the budget.** If the failure condition is deterministic (e.g. `max_tokens` too low — raising it requires a config change, not a retry), send the message directly to the DLQ or a dead-end state rather than consuming all `maxReceiveCount` retries. A fast fail on attempt 1 is cheaper than a slow fail on attempt 3.
- **Log the root cause failure prominently at ERROR level** — not just as an `edit_skipped` info event buried in processing logs. Future debugging (and alarms) depend on the failure being visible without reconstructing the call chain.
- **Add a CloudWatch alarm on your application-level "skipped work" events** (e.g. `edit_skipped`, `items_processed=0`). If a message is being retried and the work-done count is zero every time, that is operationally equivalent to a poison pill.

**Key Insight:** The SQS DLQ protects against functions that *error* — not functions that *silently succeed at doing nothing*. A Lambda that catches internal failures, logs them, and returns `{"ok": True}` looks identical to a healthy invocation from SQS's point of view. Design your handler's success/failure contract around whether real work was accomplished, not just whether the function ran to completion.
