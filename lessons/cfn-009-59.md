# Resource Signals Drop the Failure Reason; Wait Condition Handles Keep It

**Problem:** An instance with a `CreationPolicy` fails its boot script. The stack event says only `Received FAILURE signal with UniqueId i-0abc...`. The script passed `cfn-signal -e 1 --reason "dnf install failed"`, but the reason is nowhere. The rollback then terminates the instance, taking its console output and logs with it, so there's no record of which command failed.

**Root Cause:** A `CreationPolicy` (or `UpdatePolicy`) is satisfied through the `SignalResource` API, which accepts only a status and a unique ID. `cfn-signal` accepts `--reason` in both modes but has nowhere to send it in this one. A `WaitConditionHandle` is a presigned S3 URL that takes a JSON document with `Reason` and `Data` fields, and CloudFormation copies the reason into the wait condition's failure event.

**Solution:** Replace the `CreationPolicy` with a `WaitConditionHandle` plus a `WaitCondition` that depends on the instance, and pass the handle's URL (its `Ref`) to the boot script. Signal from an `EXIT` trap so every exit path reports, and record the first failing command:

```bash
failed=""
trap '[ -n "$failed" ] || failed=$BASH_COMMAND' ERR
trap 'r=$?; /opt/aws/bin/cfn-signal -e $r --reason "${failed:-ok}" "$HANDLE_URL" || :; exit $r' EXIT
set -euo pipefail
```

```yaml
BootHandle:
  Type: AWS::CloudFormation::WaitConditionHandle
Boot:
  Type: AWS::CloudFormation::WaitCondition
  DependsOn: MyInstance          # timeout starts when the instance exists
  Properties:
    Handle: !Ref BootHandle
    Count: 1
    Timeout: "1500"
```

The stack event then reads `WaitCondition received failed message: 'retry dnf install -y myapp (after 3 attempts)' for uniqueId: i-0abc...`.

**Key Insight:** If you need to know *why* a boot failed after a rollback has destroyed the evidence, the reason must travel with the signal, and only a wait condition handle carries it.
