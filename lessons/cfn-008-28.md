# CloudFormation Description Field Has a 1024-Character Limit

**Problem:** `aws cloudformation deploy` fails with `An error occurred (ValidationError) when calling the CreateChangeSet operation: Template format error: 'Description' length is greater than 1024.` If the deploy wrapper doesn't propagate the non-zero exit, the chain prints "done," the stack is silently never created, dependent stacks that `Fn::ImportValue` its exports also fail, and the feature ships with empty/unset config — surfacing much later as a confusing runtime "not configured" error.

**Root Cause:** A template's top-level `Description` field has a hard **1024-character** limit. A prose-heavy description (rationale, trade-offs, design notes) easily exceeds it. The rejection happens at change-set creation, *before* any resource is touched, so nothing is provisioned. Because it fails so early, a deploy script that swallows the error makes it look like a successful no-op.

**Solution:** Keep `Description` to a sentence or two, well under 1024 chars. Put the real design rationale in YAML `#` comments — comments have **no length limit**.

```yaml
# Full design rationale lives HERE as a comment (no length limit): why the
# bucket is public, the short-TTL-as-unshare mechanism, the trust model, the
# rejected alternatives, etc. — as long as you want.
Description: >-
  myapp artifacts stack: public S3 bucket + CloudFront distribution serving
  shared artifacts. Public-by-design, short-TTL unshare. See the note above.
```

Guard it two ways: `aws cloudformation validate-template --template-body file://template.yaml` catches an over-length Description before deploy, and your deploy wrapper must **exit non-zero on a failed `aws cloudformation deploy`** so a rejected template can never masquerade as a successful deploy. After deploying, verify the stack actually exists (`describe-stacks`) rather than trusting a "done" message.

**Key Insight:** `Description` is a capped (1024-char) docs field, not a place for prose — put the essay in comments. And a deploy that doesn't fail-fast on a CreateChangeSet error will silently ship nothing, so always confirm the stack was really created.
